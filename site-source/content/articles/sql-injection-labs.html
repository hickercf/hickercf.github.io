实战3 UNION攻击

当应用程序存在 SQL 注入漏洞，且查询结果包含在应用程序的响应中，攻击者可以利于 UNION 关键字从数据库中的 UNION 关键字从数据库的其他表中检索数据。
UNION 关键字允许一个或多个附加的 SELECT 查询，并将结果附加到原始查询。例如：

SELECT a,b FROM table1 UNION SELECT c,d FROM table2

但是该查询要生效，必须各个查询返回相同数量的列、同时各个查询每个列的数据必须兼容。
所以要进行 UNION 攻击，通常要了解：

  • 原始查询返回了多少列？
  • 原始查询返回的哪些列的数据类型适合保存注入查询的结果？

确定所需列数

执行 SQL 注入 UNION 攻击的时候，有两种有效的方法可以确认原始查询返回了多少列。
方法一：
注入一系列的 ORDER BY 子句，并不断递增，直到发生错误：

' ORDER BY 1--
' ORDER BY 2--
' ORDER BY 3--

当指定的索引超过结果集中的实际列数时，数据库会返回错误。例如：

The ORDER BY position number 3 is out of range of the number of items in the select list.

方法二：
提交一系列的 UNION SELECT 有效载荷，每个有效载荷指定不同数量的 NULL

' UNION SELECT NULL--
' UNION SELECT NULL,NULL--
' UNION SELECT NULL,NULL,NULL--

如果空值的数量和列数不匹配，数据库将返回错误，例如：

All queries combined using a UNION, INTERSECT

盲注 SQL 注入

盲注指的是应用程序存在 SQL 注入漏洞，但是其HTTP响应不显示任何包含SQL查询结果或数据库错误的详细信息。
许多攻击方式，如 UNION 注入攻击等，依赖于服务器的回显结果，对盲注 SQL 注入漏洞无效。所以必须使用不同的技术。

利用盲注 SQL 注入出发条件响应

假设有一个应用程序使用 cookie 来收集用户使用情况分析数据。发送到该应用程序的请求包含如下所示的 cookie 标头：

Cookie: TrackingId=u5YD3PapBcR4lN3e7Tj4

TrackingId 当处理包含 cookie 的请求时，应用程序会使用 SQL 查询来确认这是否是已知用户：

SELECT TrackingId FROM TrackedUsers WHERE TrackingId=u5YD3PapBcR4lN3e7Tj4

假设发送了两个请求，其中依次包含以下cookie值：

....' AND '1' = '1
....' AND '1' = '2

第一个查询会返回查询结果，因此登录成功会显示欢迎回来；第二个值导致查询不到任何结果，因为条件永为假，所以不会显示欢迎回来。
